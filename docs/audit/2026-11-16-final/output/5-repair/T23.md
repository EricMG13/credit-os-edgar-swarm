## Decisions
- Loading: a one-line `<p role="status" className="text-text-secondary">Loading the model and calculation files…</p>`, the pattern the sibling connected components already use ("Loading run activity…", "Loading report…"). D-31 allows "a skeleton or label"; the finding's suggested change names this line. No `aria-busy` was added: the status role announces it and the probe's pass condition is the status line.
- Malformed reply: a reply whose `files` is not an array now throws the existing message ("The original model and calculation files could not be listed."), the same text the 500 case shows, held in one constant so both cases cannot drift. Using the existing error path means no new state and no new component.
- The loading line shows only while `value` and `error` are both unset, so it never sits beside the error or the file list, and the two "unavailable" notes for an empty list are unchanged.

Observed, not repaired (not part of C5-012; an unusual input parked under R3): a reply that is not JSON at all, or the JSON literal `null`, makes `response.json()` or `data.files` throw a raw `SyntaxError` or `TypeError`, and `useResource` draws that error's text in the status line. The service never sends such a reply in the synthetic proof run.

Not verified: no before/after screenshot was saved (the test and probe cover the state; the loading line is plain text in the existing card); the loading label was not checked at 390 px width or in dark theme; a live service (not `proof.serve`) was not exercised; the non-JSON and `null` replies above were reasoned from the code, not run; Signal's vitest and the Python quality gate were not run, for the reasons in the table.
