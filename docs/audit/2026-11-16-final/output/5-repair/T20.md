## Decisions
- Cause: `validatedEvents` rejected the whole table when `eventRecords` dropped any row, and the
  headline chose "No dated events were published" from `rows` alone. Now the rows that can be placed
  are plotted, and every row the page cannot place (impossible date, date that does not match its
  precision, a status that is not a calendar lane, or no event name) is listed in the table's gap
  card, in a kit `Table` ("Events not placed on the calendar") with the recorded date, precision,
  published date, status and credit relevance exactly as the module wrote them, a blank cell shown
  as "Not recorded", and one source control per row to that row's Evidence line. No date is guessed
  or corrected. The card keeps the existing reason sentence "The recorded dates or precision could
  not be plotted." so the existing test that asserts it is unchanged.
- The headline says "No dated events were published for this run." only when no table carries
  events or gaps; otherwise "No published event could be placed on the calendar; the events and
  date gaps are listed below."
- Whole-table problems stay whole-table gap cards: a header row that is not the event header (the
  cells cannot be assigned to columns), and rows without a unique source line (existing behaviour,
  existing tests).
- Same lost-data class, same file: an event table that `publishedTables` cannot read (a row with
  the wrong cell count) used to vanish with no card; it now shows a gap card "The event table could
  not be read." linking to the table in Evidence. A declared event table with no rows still shows
  nothing (no event was written).
- Not changed (outside the finding, left as they were): event tables of a module whose state is
  not established or that is blocked are not drawn on the calendar; a descriptor without a lane
  name is skipped. Both are existing deliberate rules, not this finding; listed for the lead.
- R5: nothing the reader saw is removed; a row's single table-level source control is replaced by
  per-row source controls for the unplaced rows of that table.

Not verified: screen-reader output (R16); keyboard and narrow widths (R14); a live module response
with a malformed date (the probe and tests use rewritten synthetic tables).

## Review 1 (round 1, Opus medium)

Reviewer, model: Opus 5.5 (claude-opus-5-5), medium effort. Diff read: `git diff 1778835..7b1984c`.

Verdict: PASS

- Cause and surface: `validatedEvents` no longer rejects the table when `eventRecords` drops a row;
  the plottable rows are drawn and each dropped row is listed with its own source control. The
  headline "No dated events were published for this run." now shows only when there are no rows and
  no gaps. This is the finding's suggested change, on the calendar page where it was seen. C4-007
  closed.
- Callers: `buildCalendar`, `Calendar` and `upcomingCalendarRows` keep their signatures. `ReportLibrary.tsx`
  reads `calendar.rows` and `calendar.gaps.length` only; `CalendarGap.unplaced` is optional. The
  skip of a declared event table with no rows matches the base (`publishedTables` never returned a
  table with no rows, so the base skipped it too). Nothing under `web/src/pages/signal/` imports it.
- Tests and gates: no existing test or expected value changed, none skipped, no gate loosened.
- Extra repair (unreadable event table now shows the card "The event table could not be read."):
  within the finding's cause and ruling. It is the same lost-data class ("one bad row hides every
  event of the table", here a row of the wrong cell count, which made `publishedTables` drop the
  table and the base skip it silently), in the task's only file, and it adds a gap card. It removes
  nothing the reader saw (R5). Accepted.
- Wording: the new visible text is delivery's own. That is the column heads, "Not recorded" (already
  used in `Evidence.tsx` and `RunActivity.tsx`) and the headline sentence. "Events not placed on the
  calendar" is only the table's accessible name (R16: no issue raised). Every cell value comes from
  `eventDisplay(row.cells)`, the same function the plotted rows use. Dates, precision, status and
  relevance are shown exactly as written, and no date is corrected or guessed. Delivery adds no
  analysis.
- New test fails on the base: in a scratch worktree at 1778835 with only the new test copied in,
  3 of 4 tests failed (`expected [] to deeply equal [ 'Fine' ]`; the "No dated events" `<p>` present;
  unreadable table `expected [] to deeply equal [ [ …(2) ] ]`). The fourth test (empty calendar
  headline) passes on both, as expected.

Issues:

1. Low, `web/src/pages/connected/report/Calendar.tsx:250-252`: when every gap is a declared module
   gap (`descriptor.gap`) or "The event table could not be read.", the headline says "the events and
   date gaps are listed below", but no event is listed below. Only gap cards are shown. Wording
   only; nothing is lost. A neutral form such as "...; see the date gaps below" would be accurate in
   both cases.
2. Low, `web/src/pages/connected/report/Calendar.tsx:28-31,219-223`: `eventDisplay` replaces a

   plotted-row table has the same gap for its status column, which pre-dates this change. The
   unvalidated date and precision cells make it more likely here. No such row was seen in the
   probe or fixtures.

Neither issue blocks: both are Low and outside what C4-007 asks.
