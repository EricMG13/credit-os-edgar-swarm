# T04: Run page states: errors, a finished run without a report, the re-announced alert, the failed-run module state

Findings: C1-004 (run pages only), C1-005, C1-024, J5-001 (part; see NEEDS FILE). Implementer: Sonnet
worker, group repair-1. BASE (starting commit, used for the quality gate):
`bbebfef45f3bb7be929d2d5b51f2f3e8ec279103` (`audit/repair-1` with T03 and T12 merged).

## Causes

- **C1-004.** `RunProgress` drew any failed read of the run through `ErrorNotice`, one bordered line of
  red text, with the service's own word (`unknown run`) or the browser's own (`Failed to fetch`), no icon,
  no way back and no retry. The h1 of the unresolved page was `Run activity`, the breadcrumb link's words.
  The run's end reason (`run.reason`) was drawn through the same plain line.
- **C1-005.** `poll` rescheduled itself every 2 s for as long as a finished run's report answered 404,
  with no limit; the only text was `Waiting for the report to become available…`.
- **C1-024.** `poll` called `setError("")` after every successful `getRun` and then set the report's error
  again after the report request failed, so the one `role="alert"` node was removed and inserted on every
  cycle, and a screen reader announced it again each time.
- **J5-001.** `moduleWord` returned `Interrupted` for every module the run stopped at, including the one a
  failed run stopped at, so the row read `Interrupted` while the run read `Failed`; the row said nothing
  more.

## What changed

All in `web/src/pages/connected/`. No Python changed, so `react_frontend/run_activity.py` is untouched. (Round 1; superseded by Round 2, which adds `stopped_by` to `run_activity.reply`.)

- `RunProgress.tsx`
  - Two separate pieces of state, `problem` (reading the run failed) and `report` (a finished run's
    report: `pending`, `ready`, `absent`, `unreachable`, `failed`). One poll clears only its own, so an
    alert is never removed and inserted again while its text is unchanged (C1-024). The alert is one
    `Alert` element in one place, so a change of its text updates the same node.
  - A failed read of the run is an `Alert` with a title, a sentence and one action: 404 reads "This run was
    not found" (warning) with a "Back to Run activity" link, and polling stops; a fetch that never arrived
    reads "The service cannot be reached" and any other failure "The run could not be loaded" (both
    errors), each with a "Try again" button, and the page keeps polling as before. The service's own
    string is not drawn. The h1 of the page without a run is `Run`, not the breadcrumb link's `Run activity`
    (C1-004, run pages).
  - A finished run's report is waited for 10 s (`REPORT_WAIT_MS`: the first look, then a poll every 2 s
    until 10 s have passed; 6 requests in the probe), then
    the page stops polling and says "No report was published for this run" (warning) with a "Check again"
    button, and offers "Start from this run" in the header (C1-005). A report that answers a non-404 error
    shows its alert at once ("The report could not be loaded" or "The service cannot be reached") and is
    polled for the same 10 s. "Check again" asks once and is answered at once; the alert stays until the
    answer, so the pressed button keeps its place.
  - A run's end reason (`run.reason`, in the reader's sentence from T03) is an `Alert` titled "Why this
    run ended without a report": an error, or a warning for a capped run (J5-001, C1-004).
- `runFigures.ts` (round 1; round 2 narrows it to a checker stop, see Round 2): `moduleWord(state, live,
  failed)` returns `Not assessable` (rubric D-14: a failed module reads "Not assessable") for the module
  a *failed* run stopped at; `Interrupted` stays for every
  other stop (a run the service lost, a held run whose log ended). New `moduleSteps(run, live)` builds the
  run page's module rows and gives such a module one sentence from the record: "The run stopped here." and,
  when the run's log holds `draft_rejected` events for that module, "…after the checks rejected its draft
  once" or "3 times".
- `useResource.ts`: new `isUnreachable(error)` (a `TypeError` whose message is the browser's own fetch
  failure in Chrome, Firefox or Safari wording); `errorText` returns "The service cannot be reached. Try
  again, or ask whoever runs the service to check it." for it instead of the browser's "Failed to fetch".
  Every other error is passed through as before.
- `layout.tsx` and `react_frontend/run_activity.py`: not changed (see NEEDS FILE and the scope note). (Round 1; superseded: Round 2 changes `run_activity.py`.)

## NEEDS FILE: the refused module's own reason

NEEDS FILE: `src/deploy_workflow/model/handoff.py` (the `draft_rejected` event, line 952) and
`src/deploy_workflow/owners/cpos_launch.py` (`_source_gate_issues`) because the service does not record a
reason a reader could be shown for a refused module.

Evidence (run `20261117-094409-01`, produced with the pre-T12 `proof/launcher.py`, which refuses CP-4 for
lack of an agreement; run folder kept in the scratchpad, not committed):

- `_engine/state/<run>.json`: `"reason": "stopped: checker"` and nothing more.
- `runs/<run>/events.jsonl`: `{"event": "draft_rejected", "module": "CP-4", "writes_left": 2}` (then 1, 0)
  and `{"event": "stopped", "reason": "checker"}`. No reason on the rejection.
- `logs/<run>.log`: `Stopped: cpos_live_not_accepted: CP-4 not accepted within bounds`.
- The only place the cause is written is `runs/<run>/live/modules/<hash>/N.review.json`, `issues`: the
  checker's instruction to the model ("Write the method's blocked message and stop: Blocked: No executed
  governing document. The run's context declares no legal documents, ... State `module_status: Blocked` in
  the front matter, ..."). That is model-facing text, in a folder named by a hash with the module code only
  inside `invocation.json`'s system prompt, not a reason for the reader. Drawing it, or parsing it in
  `run_activity.py`, would put checker instructions on a reader page, and the AGENTS.md voice standard
  keeps such text off it.

So the module row and the run page can say, from the record, which module the run stopped at, that the
checks stopped it (T03's sentence) and how many drafts were rejected, but not that no agreement was chosen.
To name that, the recording side must write a short reader-safe reason with the rejection (for example a
`reason` field on `draft_rejected` or on the `stopped` event, written by the gate that refused), which
`run_activity._milestone` can then pass to the page. That is a vocabulary the lead should decide (it
touches `handoff.py`, `cpos_launch.py` and likely `run_events.py`), so it is not done here. The part of
J5-001 that is repaired: the module's label (`Not assessable`, not `Interrupted`), the sentence on its row,
the run's reason in an alert titled for what it explains, and the start-again action in the header. The
part not repaired: the module's own cause ("no agreement chosen") and "what to change" beyond T03's "choose
Start from this run" (the service records no cause to name).

Also: since T12, the synthetic proof no longer fails this run (a run with no agreement now finishes with a
blocked CP-4 handoff), so the J5 probe's own path no longer produces a failed run on the current tree. See
the probe section.
