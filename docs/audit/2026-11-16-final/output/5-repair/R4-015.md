# R4-015 / T45 — Synthetic execution provenance

Implemented on `audit/lead-synthetic-classification`, isolated from reviewed base
`135d2d19`. Medium finding; source registration and final integration belong to the lead.

## Cause and authority

The real scheduler invokes the normal CP-OS engine through `proof.launcher`, whose adapter
substitutes synthetic responses and rejects outbound networking. The prepared workflow records
`execution: live-provider` because that is its nominal engine route. The adapter's actual retained
`model-call/1` records instead identify both `reported_model` and `request_id` as exactly
`synthetic`. `run_activity.reply` previously returned the nominal workflow value directly.
Record correctly trusted that settled API value, replacing its pending service-mode label with
“Live provider”, “Model calls” and “HTTP status”. The report header remained “Synthetic test”.
The original Chrome and Edge diagnostics in `run-vq0vlS` show all 14 calls, including CP-1 status
200; this was a classification defect, not absent call data.

The repair reads the existing bounded, local call journal through its actual `CallRecord`
schema. A nominal provider route is classified synthetic only when every actual call has both
exact adapter markers and agrees with the workflow's pinned engine identity, scheduler issuer,
pathway, launch config and planned module. The existing identity validator binds the workflow
and `identity.json` to the scheduler record. Mixed markers, partial/malformed records, links and
unbound identities produce an explicit unknown. An absent or not-yet-started journal preserves
the nominal provider route. Explicit host-session, retained-response-replay, synthetic and
unknown manifest modes keep their existing meaning. Issuer `case_kind` never decides execution.

A related confidence check found that Record's existing fallback also replaced a *settled*
unknown with the synthetic service mode. Mode fallback is now limited to pending records.
Settled unknown or unreadable metadata shows “Unavailable” and neutral “Recorded responses” /
“Recorded status” labels. Actual live and synthetic classifications still come from the API.

## Files and smallest design

- `react_frontend/run_metadata.py`: bounded schema-aware adapter classification; reuse the
  existing pinned workflow identity validator and safe file reader.
- `react_frontend/run_activity.py`: call that classifier for the Record API execution field.
- `web/src/pages/connected/report/Record.tsx`: preserve settled unknown instead of applying the
  service-mode fallback; use neutral labels for unknown call provenance.
- `tests/test_react_runtime_identity.py`: real-scheduler execution/API regression, actual HTTP
  route check and adverse mutations of copied actual engine artifacts.
- `web/src/pages/connected/report/Record.finalAudit.test.tsx`: settled unknown, synthetic,
  host-session and retained-response controls, retaining exact call values.

Post-edit simplification considered three alternatives: renaming live globally, using issuer
case kind, or overriding API values in the UI all erase provenance distinctions. Persisting a
new scheduler adapter-mode field would add storage and settings changes although the existing
adapter records already distinguish this execution exactly. The selected implementation reuses
existing metadata readers and contracts, with two small functions and no new abstraction.
