# T01: Stop sending the server's absolute workspace path to the browser

Findings: C1-001 (High, with C5-001 merged into it). Group repair-1, implementer.
BASE (starting commit, after the coordinator's fast-forward to `audit/repair-1`):
`d8d3d634064d9591d131c605c8b6e6e1d154ee64`.
Models: rounds 1 to 3 ran on Sonnet at xhigh effort; round 4 on Opus at medium effort (ruling R12).

## Cause

`catalogue()` in `src/deploy_workflow/credit_os_catalogue.py` wrote `"workspace": str(workspace)` into
the published catalogue. `GET /connected/snapshot` (scoped or not) sends that catalogue as it was
published, so the browser received the service's absolute engine folder (probe value
`/tmp/c1p-8584g6/_engine`). Nothing reads the field: it is not drawn, and `/connected/library`
already drops it by projecting the catalogue down to `real`.

### R-1 (Medium): `GET /library/data.js` still sent `catalogue.workspace`

Cause: `service.Handler._get` serves everything under `/library/` through `Handler._file` ->
`http_base.contained_file`, so the library's `data.js` reached the browser as it lay on disk, outside
`_visible_scope`. A `data.js` from an older build (a retained preview, or a failed rebuild) still
holds the key. `/library/index.html` does not inline the data: it loads it with
`<script src="data.js">`, so `data.js` is the only route.

Repair, all in `react_frontend/__init__.py` (no file outside T01's):

- `Handler._file` is overridden: it calls the upstream `_file` unchanged (same containment, link,
  type and CSP rules) and passes a reply read from the library folder through `_library_data`.
  The override is one place, so `service.py` is not edited and `_get` is not copied.
- `_library_data(reply)` recognises the publication by its `window.CREDIT_OS_DATA=` assignment,
  not by its path, so `//data.js`, `%64ata.js`, `./data.js`, `x/../data.js`, `data.js/` and a link
  to it are all covered (a path test would miss them). It reuses the existing parser: the body of
  `_read_publication` was split into `_decode_publication(raw)` (unchanged logic) and a three-line
  `_read_publication(path)`; no second parser. A file without the key is returned as read, so a
  current `data.js` and every other library file are byte for byte what the reader gets today. A file
  with the key is re-emitted without it, in the builder's own form (ASCII, `<` as `\u003c`, as
  `update_library.embedded_json`), so the rest of the file is unchanged.
- As implemented in round 2, a file that begins with the assignment and was not the whole
  publication (invalid JSON, or lacking any of the four top-level objects, or a `catalogue` that is
  not an object) answered the fixed 500, as `/connected/snapshot` does (existing test:
  `{};console.log(0);` -> 500). Before, it was served raw. The sentence that stood here, "for the
  browser the outcome is the same", was wrong (review L-3): a file that parses but lacks `activity`
  or `chips` is one the static page opens, and round 2 made it answer 500. Round 3 narrows the
  refusal (see "Round 3"): the 500 is now only for a file that begins with the assignment and cannot
  be read as a JSON object. For such a file the browser gets no `window.CREDIT_OS_DATA` either way
  and the page states a problem either way (second review's table, from a real page in headless
  Chromium; not re-run in round 3), but its wording can differ. Every other file is answered as it
  was read, except that the key is dropped. A file not beginning with the assignment is served as it
  was.
- The file on disk is never edited by the service.

Simplest-design check (rewrite-tournament, post-edit): considered (a) intercepting
`path == "/library/data.js"` in `_get` (misses the spellings above), (b) filtering inside
`http_base.contained_file` (outside T01's files), (c) cutting the key out of the bytes with a regex
(fragile). The override plus one parse/emit function is the smallest that covers every spelling.

### R1-001 (lead ruling L6, binding): an absolute path in an issue

Ruling L6: "an absolute path reaching /connected/snapshot is a leaked path. Ruling R3 says a leaked
path is always repaired, even on an unusual input." It reverses the round-1 parking of
`credit_os_catalogue.py:220,417` (the first adversarial review's R-3 gave the cause and reach).

- Cause: `delivery_fields` catches `(Refused, OSError)` and `pinned_context` catches `(Refused,
  ContextRefused)`, and both wrote `str(error)` into `catalogue.issues`. A locked or unreadable
  handoff raises an `OSError` from `Path.read_bytes` whose text is `[Errno 13] Permission denied:
  '<absolute path of CP-1.md>'`. `catalogue.issues` is part of every snapshot, scoped or not (and
  `activity.issues` of the unscoped one), so the path reached the browser.
- Repair: both f-strings now end `({type(error).__name__})`; the sentence is otherwise unchanged
  (`<run>: delivery not catalogued (PermissionError)`, `<run>: context not used (Refused)`).
  `library_index.py:561` already words its issues this way.
- Disclosed, for the lead: the `:220` catch cannot receive an `OSError` (`Refused` texts are names
  below the run; `ContextRefused` texts are validation messages), so that line did not leak a
  server path; it is changed because L6 names it. Both issues no longer say why (`Refused` in place
  of "CP-1.md no longer has its recorded sha256"; `ContextRefused` in place of the validation
  message). Nothing in `web/src`, `apps/`, `proof/` or `react_frontend/` parses the parenthetical (the
  existing catalogue tests match only the words `context not used`), but the static library page
  draws every catalogue issue verbatim, reason included, under "Not shown", Issues
  (`apps/issuer-library/credit_os/web/views.js:1619-1626`, `libraryNotShown`), so the reader lost
  that reason (review R3-3; round 4 restores it under ruling L6b). If the owner
  wants the reason kept under R5, only the run-relative `Refused` text could return, not an
  `OSError`'s. Not touched: an `OSError` from reading the pinned context is not caught in
  `pinned_context` at all (it propagates out of `catalogue()`); that is old behaviour and not a leak.
