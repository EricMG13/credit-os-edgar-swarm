## Why not `NOT_ANALYTICAL`

`cpos_launch.NOT_ANALYTICAL` is `{"CP-MODEL", "CP-8"}` ("in the presets; each has its own route"). It names two codes with different launch rules:

- CP-MODEL: the launcher takes it in `--modules` to mean "publish the forecast" (cpos_launch.py:1041-1043, 1079).
- CP-8: the launcher refuses it in `--modules` ("it cannot be selected", cpos_launch.py:1044-1048).

CP-8 is already in `METHODS`, so today both submit-side checks let it through and the launcher refuses it later (a separate, pre-existing case, not J1-001; the page never sends CP-8). Because CP-8 is in `METHODS`, `METHODS | NOT_ANALYTICAL` and `METHODS | {"CP-MODEL"}` are the same set today: the choice changes nothing that is accepted now. The reason is meaning and drift. Reading `NOT_ANALYTICAL` as the accepted set would state in the code that CP-8 is a listable module, which is the launcher's opposite rule, and any code added to `NOT_ANALYTICAL` later would be accepted by Submit without anyone choosing it, while `METHODS` plus the single CP-MODEL code stays what the launcher takes in `--modules`. So the predicate is `METHODS` plus the single CP-MODEL code, the launcher's own rule for the one code it takes that has no method.

## Cause

CP-MODEL is a real launch code, not something the page should drop:

- `src/deploy_workflow/owners/cpos_launch.py:1041-1043`: "CP-MODEL means 'publish the forecast' (owner, 2026-11-11); it makes no model call." The launcher takes it inside `--modules`, removes it from the analytical plan, and sets `publish_forecast` from its presence. It is deliberately not in `METHODS`.
- `tests/test_start_forecast_pathways.py`: the launcher publishes the forecast only when CP-MODEL is in an explicit list, which is why the page keeps it (`web/src/pages/connected/api.ts` `PATHWAYS` equal the presets; `ConnectedApp.test.tsx` R2a-c, R4, S7, S8). The page draws no checkbox for it (`drawnModules`) but sends it. The page is right.
- Two server-side checks on a submitted module list were written against `METHODS` only and disagreed with the launcher:
  1. `scheduler.py:322` (`Scheduler.submit`) refused it with "unknown module CP-MODEL". This is the refusal the probe saw.
  2. `runs.py:254` (`_check_options`, called by `runs.command` before every launch) refused it with "run <id>: 'CP-MODEL' is not a module". Repairing only (1) lets Submit succeed and then marks the run `failed: could not be started` (scheduler.py around 633-641): the same accepted-then-failed defect in another place.

The page could not drop CP-MODEL instead: the approval digest binds `modules` between summary and Submit, and dropping it from an explicit list silently removes the forecast from a run the preset publishes it for.

A list reaches the server only when the analyst changed it (leave-out button, Advanced picker); `modules: []` (the preset) never held CP-MODEL to check, which is why ordinary runs started.
