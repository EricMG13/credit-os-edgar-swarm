# T29 (group 3): A focus-opened tooltip stays open

Base: `99ceeed` (audit/repair-3). Worktree branch `worktree-agent-a0cf44626222b2ca6`.

## Findings

- S1-005 (Medium): a tooltip that keyboard focus opens is closed again by the scroll that the same
  focus causes.

## Cause

`react-aria-components` closes a tooltip on any scroll of an ancestor of its trigger
(`useOverlayPosition` -> `useCloseOnScroll`, hard-wired in `TooltipInner`; no prop turns it off).
Tab to a trigger below the fold: the browser scrolls it into view at once, the focus handler opens
the tooltip, and the scroll event for that scroll is dispatched in the next frame's scroll steps,
which run before that frame's animation-frame callbacks. The event reaches the already-open tooltip
and closes it. A trace (focusin, tooltip added, `scroll target=MAIN` 2 ms later, tooltip removed)
is in the "before" probe output below.

## Repair

`web/src/components/base/tooltip/tooltip.tsx` only. The shared `Tooltip` now draws its overlay one
animation frame after the trigger state opens: a small internal `SettledTooltip` wraps `AriaTooltip`
and re-provides `TooltipTriggerStateContext` with `isOpen` held back until a `requestAnimationFrame`
callback has run (`useOpenAfterFrame`). The scroll event of the focus is dispatched before that
callback, so it no longer finds an open tooltip, and the tooltip is positioned against the trigger's
final place. Closing is immediate (a blur inside the frame cancels the pending draw), so nothing is
left open after focus leaves. A tooltip already open when it mounts (`isOpen`, `defaultOpen`) is drawn
at once. The context state is spread, not replaced, so `shouldSkipAnimation`, `open` and `close`
are unchanged and the warm-up behaviour between neighbouring tooltips is kept.

Every user of the shared Tooltip gets the repair: the rail (`nav-button.tsx`), `MetricCard`, library
`TraceControl` and `IssuerList`, model `MetricTile`, `StatementTable`, `TraceControl`, `button-utility`
and the Kit page. `MetricCard.tsx` is on the task's file list but needed no change: it only places the
trigger; the cause is in the shared component.

Not changed on purpose: a scroll that happens after the tooltip is open (the 3 px scroll in probe
step 3, a user scrolling with focus on the trigger) still closes it, as React Aria intends, because
the overlay is not repositioned on scroll. The finding is the scroll that the focus itself causes.

## Test

`web/src/components/base/tooltip/tooltip.focusScroll.test.tsx`, three tests. The first reproduces the
sequence in jsdom: Tab modality, `trigger.focus()`, then `fireEvent.scroll(scroller)` straight away
(the event the browser raises before the next animation-frame callback), then expects the tooltip to
be present and still present five frames later. The other two guard the new deferral: focus then
blur before the next frame leaves no tooltip (a naive deferral would leave one stuck open), and
Escape still closes a focus-opened tooltip with focus kept on the trigger.

- Before the repair: `timeout 300 npx vitest run src/components/base/tooltip/tooltip.focusScroll.test.tsx`
  gives `1 failed | 2 passed`; the failing test is "stays open when the scroll that the same focus
  caused follows it" with `TestingLibraryElementError: Unable to find role="tooltip"`.
- After the repair: `3 passed (3)`; with the existing `tooltip.test.tsx`, `2 files, 6 tests passed`.
